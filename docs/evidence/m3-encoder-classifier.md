# Phase 5 offline check: local encoders as difficulty classifiers (2026-10-04)

Question: our word-based question classifier predicts poorly which MMLU-Pro questions need a
worked answer (AUC 0.62 5-fold, 0.64 leave-one-subject-out; docs/evidence/m3-reasoning-switch.md).
vLLM Semantic Router uses small local encoders for this. Do they do better?

## Setup

- Same 980 questions and labels as the reasoning-switch evaluation. Label 1 when GLM answers
  correctly with brief working and wrongly with the letter only (210 of 980 questions differ
  between the modes; 171 of those are this case).
- Encoders, downloaded with permission (Apache-2.0 or MIT), run on gx11 CPU (8 threads,
  PyTorch fp32, batches of 16) in the recursant-privacy-eval container, offline:
  - BAAI/bge-small-en-v1.5 (33M parameters, CLS pooling);
  - vllm-sr/Vela-1.0-Encoder-307M-Embedding (vLLM Semantic Router's own embedding model,
    mean pooling);
  - Qwen/Qwen3-Embedding-0.6B (last-token pooling).
- Head: L2 logistic regression on the normalized embedding. Out-of-fold scores, 5-fold
  (seeded) and leave-one-subject-out (the subject is never seen in training).
  Script: `bench/prompt/embed_eval.py`; policy tables: `bench/prompt/reasoning_switch.py --scores`.

## Results

| Classifier | AUC 5-fold | AUC leave-one-subject-out | CPU time per question |
|---|---|---|---|
| Router's word features (context.prompt) | 0.624 | 0.635 | 0.004 ms |
| bge-small-en-v1.5 | 0.740 | 0.719 | 62 ms |
| Vela-1.0-Encoder-307M-Embedding | 0.710 | 0.697 | 264 ms |
| Qwen3-Embedding-0.6B | 0.719 | 0.714 | 1,248 ms |

The smallest encoder is the best and by far the cheapest. Policy with bge-small, scored on
subjects it never saw in training (leave-one-subject-out):

| Policy | Accuracy | Output tokens | Mean / median latency | Answers with working |
|---|---|---|---|---|
| always letter only | 66.6% | 5 | 1.7 s / 1.5 s | 0% |
| always brief working | 80.1% | 311 | 14.5 s / 6.5 s | 100% |
| bge-small, p >= 0.05 | 80.3% | 260 | 12.4 s / 5.0 s | 79% |
| bge-small, p >= 0.10 | 79.2% | 205 | 9.9 s / 2.6 s | 56% |
| bge-small, p >= 0.20 | 75.4% | 138 | 7.0 s / 1.8 s | 34% |
| word features, p >= 0.05 | 73.4% (5-fold) | 105 | 5.8 s / 1.8 s | 33% |
| hindsight oracle | 84.1% | 64 | 4.2 s / 1.6 s | 17% |

At p >= 0.10, bge-small keeps accuracy within 0.9 points of always working, with 34% fewer
output tokens, 32% lower mean latency and a 60% lower median. At the same accuracy cost the
word features cannot do that. This is the shape of vLLM Semantic Router's result: spend
reasoning only where the classifier says it helps.

## What this does and does not show

- A small local encoder predicts "this question needs working" well enough to save a third
  of the tokens at under 1 point of accuracy, on subjects it never saw.
- "Letter only" and "brief working" are prompt styles. GLM's hidden thinking adds nothing
  over brief working (m3-reasoning-switch.md), so there is no GLM thinking switch to drive
  with it.
- In the router the score has to drive a routing action, for example:
  - cheap model vs capable model on a fresh question (`simple_prompt`);
  - reasoning effort for a public reasoning model.
  Each needs labels for that model pair. Today's current pair (for example gpt-6-luna vs a
  frontier model) has not been measured.
- Costs: 62 ms of CPU per fresh question in PyTorch. An int8 ONNX Runtime build should be
  well below that, but it is not measured yet. Never on tool-result turns.

## Built: encoder in the router (off by default)

- `core/src/context/wordpiece.c`: our own WordPiece tokenizer. Matches the Hugging Face
  tokenizer on all 2,454 test texts (980 MMLU-Pro, 1,450 earlier questions, 24 hard cases:
  accents, CJK, Korean, Greek, Cyrillic, emoji, control and zero-width characters, 600-word
  input). Unicode tables generated by `bench/prompt/encoder_reference.py`.
- `core/src/context/encoder.c`: ONNX Runtime (Ubuntu `libonnxruntime` 1.23), loaded with
  dlopen only when a config asks for it. Embeddings match PyTorch to cosine 0.9999996 or
  better. No memory errors or leaks under AddressSanitizer. Router score (config path,
  `bench/prompt/score_dump.c`) matches the Python training model to 7e-11.
- `context.prompt.encoder` config section, `-DRECURSANT_ENCODER=ON` build option; spec in
  `docs/m3-request-sessions.md`. Fails closed: if an embedding fails, the turn is not
  marked simple.
- Speed (x86 dev container, CPU): 68 ms per MMLU-Pro question on 1 thread, 37 ms on 2,
  26 ms on 4; 10 ms for short questions. Only fresh user questions are embedded.

## Current model pairs (2026-10-04, US$1.68 paid)

The same 980 questions, brief working, via OpenRouter:

| Model | Correct | Cost for 980 | Output tokens per answer | Median wait |
|---|---|---|---|---|
| GLM-5.3 Flash (own GPU) | 80.1% | US$0 | 311 | 6.5 s |
| openai/gpt-6-luna | 84.6% | US$0.149 | 261 | 3.2 s |
| openai/gpt-6.1-sol | 88.3% | US$1.525 | 113 | 3.3 s |

gpt-6-luna vs gpt-6.1-sol: sol alone right on 49 questions, luna alone right on 13. That gap is
real, not noise. The largest gaps are history (+10 points), biology (+7), economics (+6) and
law (+6). In maths and chemistry the two are equal.

Can the encoder tell, from the question, where the cheap model will fail? Trained on each pair
(`bench/prompt/train.py --embeddings`, label: the cheap model is right or the expensive one is
wrong too):

| Cheap vs expensive | Word features AUC (5-fold / unseen subject) | Encoder AUC (5-fold / unseen subject) |
|---|---|---|
| luna vs sol | 0.51 / 0.47 | 0.58 / 0.56 |
| GLM vs sol | 0.47 / 0.48 | 0.57 / 0.57 |
| GLM vs luna | 0.46 / 0.42 | 0.56 / 0.58 |
| (for reference) GLM letter-only vs brief working | 0.62 / 0.64 | 0.75 / 0.72 |

The encoder beats the word features on every pair, but only just beats a coin. Measured
against simply sending a random share of questions to the expensive model:

- luna vs sol, unseen subjects, threshold 0.95: 67% to luna, 86.0% correct, 35% of sol's cost.
  A random 67/33 split gives 85.8% at 40%. The encoder adds 0.2 points and saves 5% of cost.
- GLM vs sol, unseen subjects, threshold 0.90: 50% to GLM, 85.2% correct, 59% of sol's cost.
  A random 50/50 split gives 84.2% at 50%. One point better, for more spend.

So which question a given model gets wrong is mostly not visible in the question's text. "This
question needs working" is (AUC 0.75), because that follows the subject and the shape of the
question. This matches published router results on knowledge benchmarks: learned routers
barely beat a random mix there.

## Decision

- The encoder ships off by default, as infrastructure: tested, fast enough, fails closed.
- The shipped configs keep the constant score: every fresh question goes to the cheapest
  qualified model. On current models that is the defensible choice. Always gpt-6-luna instead
  of gpt-6.1-sol costs 3.7 points for 90% less spend; always own GPU costs 8.2 points for 100%
  less public spend. A classifier does not change those trade-offs.
- Where the encoder should help is a decision that follows question type, not model quirks:
  how much working or reasoning effort to ask for (AUC 0.75 here). That needs a reasoning-effort
  arm on a public reasoning model, which has not been run.
